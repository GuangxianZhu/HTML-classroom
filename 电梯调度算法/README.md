# 电梯调度算法演示

单台电梯怎么决定下一步去哪：FCFS / SSTF / SCAN / LOOK 四种算法的动画演示。单个离线网页，没有外部依赖。

## 怎么打开

- **Windows**：双击 `启动.bat`。先 `git pull --ff-only origin main` 检查更新，再用默认浏览器打开 `index.html`。
- **其他系统 / 手机**：直接打开 `index.html`，或者用仓库首页的在线链接。

## 页面里有什么

1. **实时模拟**：和真实电梯一样，楼层外有 ▲/▼ 两个呼叫按钮（顶层只有 ▼、底层只有 ▲），乘客上车后再按目标楼层（轿厢内按钮，也可以手动按）。看电梯按所选算法移动、开关门。旁边显示请求队列、每一步的决策理由、累计移动层数、平均 / 最长等待时间，下方是楼层-时间轨迹图。
   - “制造饥饿场景”：顶楼有人等，同时中间几层不断有人按。分别用 SSTF 和 LOOK 跑一遍，对比顶楼那位等了多久。
2. **离线对比**：同一组请求（全部提前已知，类似操作系统课里的磁盘调度题）下，四种算法的路径图和总移动层数。可以先猜哪种最短再揭晓，也能把这组请求放进实时模拟里跑。
3. **原理速记**：四种算法的规则与优缺点。

## 算法简述

| 算法 | 规则 | 主要代价 |
| --- | --- | --- |
| FCFS | 按按钮被按下的顺序逐个去，途中不停 | 来回乱跑，路程最长 |
| SSTF | 永远去最近的请求，不管对方要上还是要下 | 远处请求可能饥饿 |
| SCAN | 沿一个方向扫到尽头再掉头，只顺路接同方向的外呼 | 尽头没人也要空跑 |
| LOOK | 前方没请求就掉头，只顺路接同方向的外呼 | 两端等待仍偏长 |

SCAN / LOOK 为什么只接同方向的外呼：电梯上行路过 5 楼，那里的人要下楼，接上他只会让他陪着先上去再下来，所以反方向的人等回程再接。现实中大多数电梯用的“集选控制”本质就是 LOOK。

简化假设：单台电梯、不考虑载重、乘客的目标楼层随机生成。离线对比部分假设乘客都已在车里按好目标楼层（全是内呼）。

## 文件

| 路径 | 内容 |
|---|---|
| `index.html` | 整个页面（由 `src/` 打包出来的单文件，直接打开） |
| `启动.bat` | Windows 一键启动，含 main 更新检查 |
| `重新打包.bat` | 改了 `src/` 后双击：检查更新 → 自检 → 重新打包 `index.html` → 打开（要装 Node.js，不用装包） |
| `src/algorithms.js` | 四种算法的纯函数实现（`stops()` 到站时停不停、接谁；`decide()` 不停时往哪走），浏览器和 Node 通用 |
| `src/app.js` | 实时模拟、轨迹图、离线对比的界面和动画 |
| `src/index.html`、`src/style.css` | 页面骨架和样式 |
| `tests/algorithms.test.js` | 用教材经典磁盘调度例子和带方向外呼的场景校验算法，再跑 2000 组随机场景确认都能处理完 |
| `build.mjs` | 把 `src/` 内联成单文件 `index.html` |

手动打包：

```bash
node tests/algorithms.test.js   # 自检
node build.mjs                  # 生成 index.html
```
